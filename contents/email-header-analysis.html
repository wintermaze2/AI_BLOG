이메일 헤더 분석 방법

이메일 헤더에는 메일이 어디에서 발송되었고 어떤 서버를 거쳐 전달되었는지, SPF·DKIM·DMARC 인증 결과는 어떠했는지 등을 확인할 수 있는 정보가 담겨 있습니다. 이 글에서는 실제 이메일 헤더의 주요 항목을 읽고, 스팸메일이나 발송 오류를 분석하는 방법을 설명합니다.

이메일 헤더란 무엇인가요?

이메일을 열어보면 보통 발신자, 수신자, 제목, 본문만 보이지만 실제 메시지에는 다양한 기술 정보가 함께 포함되어 있습니다. 이것이 이메일 헤더입니다.

헤더에는 발송 서버와 수신 서버의 정보, 메시지 식별자, 인증 결과, 전달 경로 등이 기록됩니다. 메일 서비스에 따라 일부 항목은 사용자 화면에서 숨겨져 있지만 원본 메시지를 확인하면 더 많은 정보를 볼 수 있습니다.

이메일 헤더에서 먼저 확인할 항목

헤더주요 역할
From사용자에게 표시되는 발신자 주소입니다.
Return-Path반송 메일이 전달될 주소입니다.
Received메일이 어떤 서버를 거쳐 전달되었는지 보여줍니다.
Authentication-ResultsSPF, DKIM, DMARC 등의 인증 결과를 보여줍니다.
DKIM-SignatureDKIM 서명에 사용된 도메인과 검증 정보를 포함합니다.
Message-ID메일 메시지를 식별하기 위한 고유 식별자입니다.

From: 사용자가 보는 발신자 주소

From: MailLink <newsletter@example.com>

From은 사용자가 보는 발신자 이름과 이메일 주소입니다. 하지만 이것만으로 실제 메일 발송 서버나 발신자를 판단해서는 안 됩니다. 실제 발송 서버는 Received, SPF, DKIM, DMARC 등의 정보를 함께 확인해야 합니다.

Return-Path: 반송 주소

Return-Path: <bounce@example.com>

Return-Path는 메일이 정상적으로 전달되지 않았을 때 반송 메시지를 받을 주소입니다. 대량 이메일 발송 시스템에서는 From과 Return-Path를 다르게 사용하는 경우가 흔합니다.

따라서 두 주소가 다르다는 사실 자체가 악성 메일이라는 의미는 아닙니다.

Received: 메일이 지나온 경로

Received: from mail.example.com (mail.example.com [203.0.113.10])
        by mx.receiver.example with ESMTPS
        id ABC123
        for <user@example.net>;
        Fri, 21 Aug 2026 09:20:10 +0900

Received에는 메일을 받은 서버가 어떤 서버로부터 메시지를 전달받았는지에 대한 정보가 기록됩니다. 메일이 여러 서버를 거쳤다면 여러 개의 Received 헤더가 존재할 수 있습니다.

Received 헤더는 아래쪽부터 읽어보세요

새로운 서버는 일반적으로 자신의 Received 기록을 헤더 상단에 추가합니다. 따라서 여러 개가 있다면 보통 아래쪽에서 위쪽으로 올라가면서 전달 경로를 추적하면 이해하기 쉽습니다.

발송 서버
   ↓
릴레이 서버
   ↓
수신 서버

다만 외부에서 전달된 헤더는 신뢰할 수 없는 정보가 포함될 수 있으므로 모든 Received 값을 무조건 사실로 간주해서는 안 됩니다. 수신 서버가 신뢰하는 경계를 고려하여 해석해야 합니다.

Authentication-Results: 인증 결과 확인

Authentication-Results: mx.example.net;
        spf=pass smtp.mailfrom=example.com;
        dkim=pass header.d=example.com;
        dmarc=pass header.from=example.com
항목의미
spf=passSPF 검증이 통과했다는 의미입니다.
dkim=passDKIM 서명 검증이 통과했다는 의미입니다.
dmarc=passDMARC 검증이 통과했다는 의미입니다.

예를 들어 spf=fail, dkim=pass, dmarc=fail이라면 DKIM은 통과했지만 SPF와 DMARC에서 문제가 발생한 것입니다.

다만 인증 결과만으로 메일이 정상 메일인지 판단해서는 안 됩니다. 인증에 성공한 정상 메일도 스팸으로 분류될 수 있고, 특정 인증이 실패했다고 해서 반드시 악성 메일이라고 단정할 수도 없습니다.

SPF 결과에서 smtp.mailfrom 확인하기

spf=pass smtp.mailfrom=bounce.example.com

SPF는 SMTP 대화에서 사용되는 MAIL FROM, 즉 Envelope From을 기준으로 검증합니다. 따라서 SPF가 확인하는 도메인과 사용자가 보는 From 주소가 반드시 같지는 않습니다.

DKIM-Signature에서 확인할 항목

DKIM-Signature: v=1; a=rsa-sha256; d=example.com;
        s=selector1; c=relaxed/relaxed;
        h=from:to:subject:date:message-id;
        bh=...;
        b=...
값의미
vDKIM 버전입니다.
a서명에 사용된 알고리즘입니다.
dDKIM 서명을 생성한 도메인입니다.
sDKIM selector입니다.
h서명에 포함된 헤더 목록입니다.
bh서명된 본문을 기준으로 계산된 해시 값입니다.
bDKIM 전자서명 값입니다.

DKIM selector는 왜 필요한가요?

s=selector1 같은 값은 공개키를 조회할 DNS 레코드를 결정하는 데 사용됩니다.

DKIM-Signature: v=1; d=example.com; s=selector1; ...

수신 서버는 일반적으로 다음 형태의 DNS 이름에서 공개키를 조회합니다.

selector1._domainkey.example.com

따라서 헤더의 d와 s를 확인하면 DKIM 설정이 어떤 도메인과 selector를 사용하는지 파악할 수 있습니다.

DMARC 결과에서는 From 도메인을 함께 확인하세요

DMARC는 SPF와 DKIM이 각각 성공했는지만 보는 기술이 아닙니다. 인증에 사용된 도메인과 사용자가 보는 From 도메인의 정렬(Alignment) 여부도 중요합니다.

From: news@example.com

Authentication-Results:
    spf=pass smtp.mailfrom=mailer.example.com;
    dkim=pass header.d=example.com;
    dmarc=pass header.from=example.com

DMARC 문제를 분석할 때는 단순히 dmarc=fail이라는 결과만 확인하지 말고 header.from, smtp.mailfrom, header.d를 함께 확인하는 것이 좋습니다.

Message-ID는 무엇을 확인하는 데 사용하나요?

Message-ID: <20260821092010.123456@example.com>

Message-ID는 메시지를 식별하기 위한 값입니다. 메일 발송 시스템의 로그와 수신자가 제공한 헤더를 비교할 때 유용한 단서가 될 수 있습니다.

여러 헤더를 연결해서 분석해야 합니다

From: marketing@example.com
Return-Path: <bounce@example.com>

Received: from mail.example.com [203.0.113.10]
        by mx.receiver.example

Authentication-Results: mx.receiver.example;
        spf=pass smtp.mailfrom=example.com;
        dkim=pass header.d=example.com;
        dmarc=pass header.from=example.com

이 정보를 연결하면 사용자가 보는 발신 주소, 반송 주소, 메일을 전달한 서버, 발송 IP, SPF·DKIM·DMARC 인증 결과를 함께 파악할 수 있습니다.

스팸메일을 분석할 때의 기본 순서

  1. From에서 사용자가 보는 발신 주소를 확인합니다.
  2. Return-Path에서 반송 주소를 확인합니다.
  3. Received를 통해 전달 경로와 발송 IP를 확인합니다.
  4. Authentication-Results에서 SPF, DKIM, DMARC 결과를 확인합니다.
  5. DKIM-Signature에서 서명 도메인과 selector를 확인합니다.
  6. From 도메인과 SPF/DKIM 인증 도메인의 관계를 확인합니다.
  7. 본문에 포함된 링크의 도메인과 실제 연결 주소를 확인합니다.
  8. 필요하다면 발송 시스템의 로그와 Message-ID 등을 비교합니다.

헤더만으로 스팸 여부를 확정할 수 있을까요?

헤더는 매우 중요한 분석 자료이지만 헤더만으로 메일의 악성 여부를 100% 확정할 수 있는 것은 아닙니다.

예를 들어 SPF, DKIM, DMARC가 모두 통과한 피싱메일도 존재할 수 있습니다. 공격자가 자신의 도메인을 사용하고 정상적으로 인증을 설정했다면 인증 자체는 정상적으로 통과할 수 있기 때문입니다.

따라서 보안 분석에서는 인증 결과와 함께 발신 도메인, IP 평판, 링크, 첨부파일, 본문 내용, 발송 패턴 등을 종합적으로 확인해야 합니다.

이메일 헤더 분석에서 자주 하는 실수

From 주소만 보고 발신 서버를 판단하는 경우

From은 사용자가 보는 발신 주소일 뿐 실제 SMTP 연결을 수행한 서버를 직접 의미하지 않습니다. 발송 서버를 확인하려면 Received와 인증 관련 헤더를 함께 확인해야 합니다.

SPF pass를 보고 안전한 메일이라고 판단하는 경우

SPF는 해당 도메인을 대신해 메일을 보낼 수 있는 서버인지 확인하는 기술입니다. SPF 통과 자체가 메일의 내용이 안전하다는 의미는 아닙니다.

DKIM pass를 보고 발신자가 신뢰할 수 있다고 판단하는 경우

DKIM은 서명된 메시지와 서명 도메인을 검증하는 기술입니다. 악성 발신자가 자신의 도메인에 DKIM을 정상적으로 설정하는 것도 가능합니다.

Received의 모든 IP를 실제 발송 IP라고 생각하는 경우

메일은 여러 서버를 거쳐 전달될 수 있습니다. 또한 헤더에는 신뢰할 수 있는 서버가 기록한 정보와 외부에서 전달된 정보가 함께 존재할 수 있으므로, 수신 서버가 신뢰하는 경계를 고려하여 해석해야 합니다.

이메일 헤더 분석은 메일 보안의 출발점입니다

이메일 헤더는 메일의 이동 경로와 인증 상태를 확인할 수 있는 중요한 자료입니다. 특히 From → Return-Path → Received → Authentication-Results → DKIM-Signature 순서로 주요 항목을 확인하는 습관을 들이면 스팸메일, 피싱메일, 인증 오류, 발송 경로 문제를 훨씬 쉽게 분석할 수 있습니다.

그리고 SPF·DKIM·DMARC가 모두 통과한 메일이라고 하더라도 그것만으로 안전한 메일이라고 단정해서는 안 됩니다. 인증은 발신자를 검증하는 중요한 단계이지만 실제 이메일 보안은 발신자 평판과 콘텐츠, 링크, 첨부파일, 수신자 반응 등을 함께 고려해야 하기 때문입니다.

이메일 헤더를 분석한다는 것은 “누가 보냈는가”뿐 아니라 “어떤 서버를 거쳐 왔고, 어떤 인증을 통과했으며, 수신 서버가 무엇을 확인했는가”를 추적하는 과정입니다.

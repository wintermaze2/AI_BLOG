DKIM(DomainKeys Identified Mail, 도메인키 식별 메일)은 이메일이 발송된 출처를 인증하고, 전송 도중 메시지가 위·변조되지 않았는지를 확인할 수 있게 해 주는 이메일 인증 기술입니다. 이 글에서는 DKIM의 동작 원리와 DKIM-Signature 헤더의 각 태그가 어떤 의미인지, 그리고 메일링크를 이용해 메일을 발송할 때 필요한 DNS 레코드 등록 방법을 순서대로 설명합니다.

DKIM은 무엇을 보장하나요?

DKIM은 공개키 암호화 방식의 디지털 서명을 이용합니다. 발송자가 개인키로 메일에 서명하면, 수신 서버는 DNS에 공개된 공개키로 그 서명을 검증합니다. 이를 통해 다음 두 가지를 확인할 수 있습니다.

  • 발신 도메인의 진위 — 서명에 사용된 개인키를 가진 주체가 실제로 해당 도메인의 관리자임을 확인합니다.
  • 메시지 무결성 — 서명 이후 본문이나 주요 헤더가 중간에서 변경되지 않았음을 확인합니다.

다만 DKIM 자체는 "이 메일을 수신할지 말지"를 결정하지 않습니다. 검증에 실패해도 메일이 반드시 차단되는 것은 아니며, 처리 방식은 전적으로 수신 측 정책에 달려 있습니다. DKIM은 인증 수단일 뿐 이메일 송수신에 필수적인 항목은 아니기 때문입니다. 실제 처리 정책을 지정하려면 DMARC를 함께 사용해야 합니다.

작동 방식

전체 흐름은 다음과 같습니다.

  1. 발송자가 공개키/개인키 쌍을 생성합니다.
  2. 공개키를 DNS 서버에 등록해 누구나 조회할 수 있게 합니다.
  3. 메일 발송 시 개인키로 서명한 DKIM-Signature 헤더를 만들어 메일에 삽입합니다.
  4. 수신 서버는 DNS 질의로 공개키를 가져와 서명을 검증합니다.

1단계 — 키 쌍 생성과 공개키 등록

개인키는 외부에 노출되지 않도록 관리하고, 공개키는 DNS에 TXT 레코드로 등록합니다. 적용할 도메인을 example.net이라고 가정하겠습니다.

항목값
이름(호스트) selector._domainkey 또는 selector._domainkey.example.net
유형(Record Type)TXT
값(Value) v=DKIM1; k=rsa; p=MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8A...

selector 부분은 사용자가 정하는 이름입니다. s1, mail, dkim처럼 식별 가능한 영문 단어를 쓰면 됩니다. 하나의 도메인에 서로 다른 셀렉터로 여러 개의 키를 동시에 등록할 수 있어, 발송 시스템별로 키를 분리하거나 키를 교체할 때 유용합니다. _domainkey는 고정값이므로 그대로 사용해야 합니다.

값에 들어가는 태그의 의미는 다음과 같습니다.

태그설명
v버전. DKIM1 고정값입니다.
k키 타입. 생략하면 rsa로 간주합니다. RFC 8463에서 ed25519가 추가되었으나 아직 지원하지 않는 수신 서버가 있어, 사용한다면 RSA 키와 병행 등록하는 것이 안전합니다.
pBase64로 인코딩한 공개키입니다. 위 예시는 형식을 보여 주기 위해 줄인 것이므로 반드시 직접 생성한 키를 입력해야 합니다.
t선택. t=y는 테스트 모드로, 수신 서버에 검증 실패를 정책에 반영하지 말라고 요청합니다.
등록 시 자주 발생하는 문제

따옴표 — 자료에 따라 값 전체가 큰따옴표로 묶여 있는 경우가 있는데, 대부분의 DNS 관리 콘솔은 따옴표 없이 값만 입력해야 합니다. 문서에서 복사할 때 곡선 따옴표(“ ”)가 섞여 들어가면 등록에 실패합니다.

255바이트 제한 — DNS TXT 레코드는 문자열 하나가 255바이트를 넘을 수 없습니다. 2048비트 RSA 공개키는 이 길이를 초과하므로, 값을 여러 문자열로 나누어 입력해야 합니다. 관리 콘솔이 자동으로 분할해 주는 경우도 있고, 직접 "앞부분" "뒷부분" 형태로 나누어 넣어야 하는 경우도 있으니 등록 후 반드시 조회해서 확인하시기 바랍니다.

키 길이 — 1024비트 키도 동작하지만, 2024년부터 주요 메일 서비스가 대량 발송자에게 2048비트를 권고하고 있습니다. 신규 발급 시에는 2048비트를 사용하시기 바랍니다.

2단계 — DKIM-Signature 헤더 생성

발송자는 메일 헤더와 본문을 이용해 서명을 만들고, 이를 DKIM-Signature 헤더로 원본 헤더에 추가합니다. 이 헤더는 평소에는 보이지 않으며, 포털 등에서 제공하는 "메일 원문 보기" 기능으로 확인할 수 있습니다.

DKIM-Signature: v=1; a=rsa-sha256; d=example.net; s=news;
 c=relaxed/relaxed; t=1126524832; x=1149015927;
 h=from:to:subject:date:reply-to:message-id;
 bh=2jUSOH9NhtVGCQWNr9BrIAPreKQjO6Sn7XIkfJVOzv8=;
 b=hyjCnOfAKDdLZdKIc9G1q7LoDWlEniSbzc+yuU2zGrtruF00ldcFVoG4WTHNiYw...
태그필수설명
v필수 버전 정보이며 항상 1입니다.
a필수 서명 알고리즘입니다. 대부분 rsa-sha256을 사용합니다.
d필수 서명 도메인입니다. 이 값이 DMARC 판정의 기준이 됩니다.
s필수 셀렉터입니다. d와 조합해 공개키를 조회합니다. 위 예시는 d=example.net, s=news이므로 news._domainkey.example.net에 TXT 질의를 보냅니다.
h필수 서명에 포함된 헤더 목록입니다. 나열된 순서대로 서명했으므로 검증 시에도 같은 순서로 처리해야 합니다. 여기에 없는 헤더는 중간에 추가·변경되어도 검증에 영향을 주지 않습니다.
bh필수 본문 해시(body hash)를 Base64로 인코딩한 값입니다. 해시 알고리즘은 임의 길이의 입력을 고정 길이 값으로 변환하며, 한 글자만 달라져도 결과가 완전히 바뀝니다. 수신 측은 받은 본문의 해시를 직접 계산해 이 값과 비교함으로써 본문 변조 여부를 판단합니다.
b필수 개인키로 만든 서명 값입니다. h에 나열된 헤더와 DKIM-Signature 헤더 자체(단, b= 값은 비운 상태)를 대상으로 서명합니다. 수신 측은 공개키로 이 서명을 검증합니다.
c선택 정규화(canonicalization) 방식을 헤더/본문 형식으로 지정합니다. simple은 한 글자도 달라지면 안 되고, relaxed는 전송 과정에서 흔히 생기는 공백이나 줄바꿈 차이를 허용합니다. 생략 시 simple/simple이지만, 중계 서버를 거치며 검증이 깨지는 것을 막기 위해 실무에서는 relaxed/relaxed를 사용합니다.
t / x선택 서명 생성 시각과 만료 시각을 UNIX 타임스탬프로 나타냅니다.

b 값은 실제로는 훨씬 길며, 위 예시는 지면상 줄인 것입니다.

3단계 — 수신 측 검증

수신 서버는 d와 s로 공개키를 조회한 뒤 두 가지를 확인합니다. 본문 해시를 직접 계산해 bh와 비교하고, 공개키로 b 서명을 검증합니다. 둘 다 통과하면 DKIM 검증에 성공한 것입니다.

DKIM만으로는 부족한 이유

여기서 중요한 점이 있습니다. DKIM 검증은 DKIM-Signature 헤더에 담긴 정보만으로 이루어지며, 수신자에게 보이는 From 주소와는 아무 관련이 없습니다. 즉 아무 도메인으로 서명해도 서명 자체는 유효하게 통과할 수 있습니다.

이 간극을 메우는 것이 DMARC의 정렬(alignment) 개념입니다. DMARC는 DKIM 검증 성공 여부뿐 아니라 d 태그의 도메인이 From 주소의 도메인과 일치하는지까지 확인합니다. 따라서 DKIM을 적용하더라도 두 도메인이 다르면 DMARC 판정에는 실패하게 됩니다.

DMARC의 동작 방식과 정책 레코드 작성법은 DMARC에 대하여 알아보기 문서에서 자세히 다루고 있습니다.

메일링크 이용 시 DNS 레코드 등록 방법

메일링크는 기본적으로 메일링크 소유 도메인으로 DKIM-Signature를 작성합니다. 따라서 d와 s 태그에는 메일링크와 관련된 값이 들어갑니다.

예를 들어 메일링크 사용자가 보내는사람 주소로 reply@example.net을 사용한다고 가정해 보겠습니다. 이 주소는 From 헤더에 들어가지만 서명 도메인은 메일링크 쪽이므로, 두 도메인이 서로 달라집니다. 일반적인 DKIM 검증만 수행하는 환경에서는 문제가 없지만, From 도메인과 서명 도메인의 일치를 요구하는 환경에서는 메일이 전달되지 않거나 스팸편지함으로 분류될 수 있습니다.

이 문제를 해결하려면 사용자 소유 도메인의 DNS에 메일링크의 DKIM 서버를 연결하는 CNAME 레코드를 추가해야 합니다. 앞서 설명한 방법이 직접 키 쌍을 만들어 TXT로 등록하는 방식이었다면, 메일링크의 DKIM 서비스를 이용할 때는 다음과 같이 등록합니다. 사용자 도메인은 example.net이라고 가정합니다.

항목값
이름(호스트)mlk._domainkey 또는 mlk._domainkey.example.net
유형(Record Type)CNAME
값(Value)dkim.maillink.co.kr

CNAME 방식이므로 키 생성과 교체는 메일링크가 담당하며, 고객사에서 개인키를 직접 보관하거나 관리할 필요가 없습니다.

이 레코드가 정상적으로 등록되면 메일링크는 d=example.net으로 서명하게 되어 From 도메인과 서명 도메인이 일치합니다. 결과적으로 DMARC의 DKIM 정렬 조건을 충족하며, 엄격한 발신자 인증 규칙을 적용하는 메일 서비스의 요구도 만족시킬 수 있습니다.

등록 후 확인 방법

DNS 반영에는 보통 수십 분에서 하루 정도가 걸립니다. 메일링크 사용자라면 별도의 도구 없이 화면에서 바로 확인하실 수 있습니다.

메일링크 접속 → 이메일 발송 → 보내는이 주소 관리로 이동한 뒤, 목록에 보이는 도메인을 더블클릭하면 정상 등록 여부가 표시됩니다.

직접 DNS를 조회해 확인하려면 아래 명령을 사용합니다.

nslookup -type=CNAME mlk._domainkey.example.net

메일을 실제로 발송한 뒤 "메일 원문 보기"에서 DKIM-Signature 헤더의 d= 값이 사용자 도메인으로 표시되는지 확인하시면 확실합니다.

추가적인 문의 사항은 메일링크 고객센터(1544-9231 또는 help@maillink.co.kr)로 연락 주시기 바랍니다.

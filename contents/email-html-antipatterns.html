웹에서는 아무 문제 없는 HTML이 이메일에서는 그대로 깨집니다. 레이아웃이 무너지거나, 태그가 통째로 제거되거나, 아예 스팸으로 분류되기도 합니다. 이 글에서는 이메일 본문에 쓰면 안 되는 HTML 태그와 CSS를 정리하고, 각각을 무엇으로 바꿔야 하는지 설명합니다.

이메일 HTML이 웹과 다른 이유

브라우저는 최신 웹 표준을 따르지만 메일 클라이언트는 그렇지 않습니다. 차이를 만드는 원인은 크게 세 가지입니다.

  • 렌더링 엔진이 다릅니다. 윈도우용 Outlook 데스크톱 버전은 2007년부터 브라우저 엔진이 아니라 워드(Word)의 문서 엔진으로 메일을 그립니다. 워드는 웹 레이아웃을 위해 만들어진 것이 아니라서 현대 CSS의 상당 부분을 그냥 무시합니다.
  • 보안상 제거됩니다. 메일은 모르는 사람이 보내오는 문서입니다. 이메일 클라이언트는 스크립트를 실행하지 않고, 외부 리소스를 불러오는 태그를 걷어냅니다.
  • 웹메일은 남의 페이지 안에 들어갑니다. Gmail이나 네이버 메일은 자기 웹페이지 한가운데에 메일 본문을 끼워 넣습니다. 그래서 문서 전체를 규정하는 태그는 살아남을 수 없습니다.

결론적으로 이메일 HTML은 최대한 단순하게 작성해야 합니다. 웹에서 쓰던 최신 기법을 그대로 옮기지 말고, 꼭 필요한 태그와 속성만 남기는 것이 안전합니다.

절대 넣지 말아야 할 태그

아래 태그들은 대부분의 클라이언트에서 제거되거나 동작하지 않습니다. 효과가 없을 뿐 아니라 스팸 점수만 올라갑니다.

태그무슨 일이 생기나대안
<script> 모든 주요 클라이언트가 제거합니다. 동작하지 않으면서 스팸 판정에는 강한 감점 요인이 됩니다. 메일 안에서 동작이 필요하다면 설계를 다시 하세요. 랜딩 페이지로 보내는 것이 정답입니다.
<iframe> 거의 모든 곳에서 차단됩니다. 빈 영역만 남습니다. 대표 이미지와 링크
<form> <input> Gmail은 제거하고, 남아 있어도 제출이 되지 않는 환경이 많습니다. 수신자에게는 눌러도 반응 없는 폼이 됩니다. 설문·구독 페이지 링크
<embed> <object> 차단됩니다. 과거 악성코드 유포에 쓰였던 태그라 필터가 민감하게 반응합니다. 이미지와 링크
<video> <audio> 재생되는 클라이언트가 소수입니다. 대부분 아무것도 보이지 않습니다. 재생 버튼을 합성한 썸네일 이미지를 영상 페이지로 링크
<meta http-equiv="refresh"> 무시되며, 자동 이동은 피싱의 전형적 수법이라 위험 신호로 취급됩니다. 본문에 명시적인 링크
<base> 무시되는 경우가 많아 상대 경로 링크가 통째로 깨집니다. 모든 링크와 이미지에 절대 URL 사용
<link rel="stylesheet"> 외부 CSS는 불러오지 않습니다. 스타일이 전부 빠진 맨 HTML이 보입니다. 인라인 style 속성

레이아웃은 div가 아니라 table로

웹 개발에서 <table>로 레이아웃을 잡는 것은 오래전에 사라진 관습입니다. 그런데 이메일에서는 여전히 table이 정답입니다. Outlook은 워드 엔진이 현대 레이아웃 CSS를 지원하지 않고, 네이버·다음은 본문을 자기 페이지에 끼워 넣으면서 문서 구조를 손보기 때문입니다. 같은 화면을 <div>로 짠 것과 <table>로 짠 것을 나란히 보내 보면 차이가 분명하게 드러납니다.

속성 · 태그주요 클라이언트에서 벌어지는 일
display:flexOutlook 데스크톱이 무시합니다. 나란히 놓으려던 요소가 세로로 쌓입니다.
display:gridOutlook 데스크톱이 무시합니다. 마찬가지로 배치가 무너집니다.
position:absolute fixedOutlook 데스크톱이 무시합니다. 겹치게 배치한 요소가 아래로 흘러내립니다.
floatOutlook에서 불안정합니다. 2단 구성이 1단으로 바뀌는 일이 잦습니다.
max-widthOutlook 데스크톱이 무시합니다. 폭 제한이 걸리지 않아 본문이 화면 끝까지 늘어납니다.
<body> 와 거기에 준 스타일네이버·다음이 제거합니다. <body> 에 지정한 배경색·여백·기본 글꼴이 통째로 사라집니다.
<div> 중첩 레이아웃네이버·다음에서 배치가 어긋나는 사례가 잦습니다. 같은 구조라도 <table> 로 짠 쪽이 안정적입니다.

2단 배치를 예로 들면 다음과 같이 바꿔야 합니다.

<!-- 이렇게 하지 마세요 -->
<div style="display:flex;gap:20px;">
  <div style="flex:1;">왼쪽 내용</div>
  <div style="flex:1;">오른쪽 내용</div>
</div>

<!-- 이렇게 하세요 -->
<div style="background:#f5f6f8;padding:20px 0;">
  <table role="presentation" align="center" width="600"
         cellpadding="0" cellspacing="0" border="0">
    <tr>
      <td width="290" valign="top">왼쪽 내용</td>
      <td width="20">&nbsp;</td>
      <td width="290" valign="top">오른쪽 내용</td>
    </tr>
  </table>
</div>
가장 바깥은 div, 그 안에 table

네이버와 다음은 메일 본문을 자기 웹페이지에 끼워 넣으면서 <body> 를 제거합니다. 그래서 <body> 에 배경색이나 여백을 지정해 두면 그대로 사라집니다. 전체 배경처럼 바깥을 감싸는 스타일이 필요하다면 가장 바깥에 <div> 를 두고 거기에 인라인으로 지정한 뒤, 그 안에서 <table> 로 내용을 잡으세요.

role="presentation" 을 빼먹지 마세요

레이아웃 목적의 table에는 role="presentation" 을 넣어야 합니다. 이것이 없으면 스크린리더가 데이터 표로 인식해 "3열 1행 표"처럼 읽어버립니다. 시각장애인 수신자에게는 내용을 따라가기 어려운 메일이 됩니다.

CSS는 인라인으로

이메일에서 가장 안전한 방식은 각 태그의 style 속성에 직접 쓰는 것입니다. <style> 블록은 대부분 제거됩니다. 국내 수신자 비중이 가장 큰 네이버 메일은 <style> 블록과 <link> 로 불러온 외부 CSS를 삭제하므로, 거기에 정의한 글꼴·색상·레이아웃 규칙은 아예 적용되지 않습니다. Gmail은 <style> 자체는 받아들이지만 지원하지 않는 속성을 걸러내기 때문에 작성자의 의도와 다르게 보이는 경우가 많고, 본문이 길어 잘릴 때(클리핑)나 메일이 전달될 때는 통째로 떨어뜨립니다. 어느 쪽이든 <style> 이 살아남는다고 가정하고 만들면 안 됩니다.

rem em vw 단위 기준값이 클라이언트마다 달라 크기를 예측할 수 없습니다. px를 쓰세요.

기본 여백도 믿지 마세요

<p>와 <h1>~<h6>의 기본 여백은 클라이언트마다 다릅니다. 어떤 곳에서는 문단 간격이 두 배로 벌어집니다. 여백이 중요한 자리라면 margin을 직접 지정하거나, 아예 빈 <td>로 간격을 만드는 편이 예측 가능합니다.

스팸 필터를 자극하는 코드

렌더링과 별개로, 코드 자체가 위험 신호가 되는 경우도 있습니다.

  • 숨김 텍스트 — display:none, font-size:0, 배경과 같은 색의 글자. 필터를 속이려는 전형적 수법으로 학습돼 있습니다.
  • 표시 문구와 실제 링크가 다른 경우 — 화면에는 example.com이라고 쓰고 href는 다른 도메인으로 보내는 형태. 피싱의 기본 패턴입니다.
  • 단축 URL 남발 — 최종 목적지를 감추므로 신뢰도가 떨어집니다.
  • 닫히지 않은 태그와 깨진 중첩 — 파싱이 실패하면 필터는 의도적인 난독화로 의심합니다.

본문을 이미지 한 장으로 채우거나 이미지 맵으로 링크를 거는 방식도 강한 감점 요인입니다. 이 주제는 이미지 뉴스레터가 스팸함으로 가는 이유와 해결법에서 자세히 다루고 있습니다.

발송 전 코드 점검

  • <script>, <iframe>, <form>, <video>가 없는가
  • 레이아웃을 table로 잡았고 role="presentation"을 넣었는가
  • 모든 스타일이 인라인인가, 외부 CSS를 참조하지 않는가
  • 모든 링크와 이미지가 https 절대 URL인가
  • 배경 이미지에 bgcolor 대체값이 있는가
  • 이미지를 모두 차단한 상태로 열어도 내용이 전달되는가
  • 크기 단위가 px인가
  • Outlook 데스크톱과 Gmail 웹에서 각각 확인했는가
실제로 열어보는 것을 대신할 방법은 없습니다

코드를 아무리 규칙에 맞게 써도 클라이언트별 차이는 남습니다. 본 발송 전에 반드시 자신에게 시험 발송해서, 최소한 Outlook 데스크톱과 Gmail 웹 두 곳에서 직접 열어 확인하시기 바랍니다. 이 둘에서 문제가 없으면 나머지는 대체로 무난합니다.

SPF(Sender Policy Framework)는 발신자 주소를 조작해 수신자가 정당한 발신자로 오인하게 만드는 스푸핑(spoofing)을 막기 위한 이메일 인증 기술로, RFC 7208에서 표준으로 정의되어 있습니다. 이 글에서는 SPF가 어떤 주소를 기준으로 무엇을 검사하는지, 레코드를 어떻게 작성하는지, 그리고 메일링크를 이용해 메일을 발송할 때 필요한 DNS 등록 방법을 설명합니다.

발신자 주소는 두 종류입니다

SPF를 이해하려면 이메일에 발신자 주소가 두 개 존재한다는 사실부터 알아야 합니다.

구분설명
Return Path
(반송 주소)		 SMTP 프로토콜의 MAIL FROM 명령에 사용되는 주소입니다. 전송 중 오류가 발생했을 때 반송 메일이 돌아가는 경로이며, 수신자에게는 보이지 않습니다. SPF가 검사하는 대상이 바로 이 주소입니다.
From
(보낸사람)		 메일 헤더에 담기는 주소로, 수신함에서 "보낸사람"으로 표시됩니다. 수신자가 발신인을 식별하는 기준이 되는 주소입니다.

두 주소가 같을 수도 있지만 다른 경우도 많습니다. 메일링크를 이용해 메일을 보낼 때 사용자는 보내는사람 주소로 개인 이메일이나 회사 대표 주소를 사용하지만, SMTP 통신에서 쓰이는 Return Path는 반송 메일 수집을 위해 별도로 설정됩니다.

SPF는 어떻게 동작하나요?

SPF는 Return Path 주소의 도메인 부분(@ 뒤쪽)에 DNS 질의를 보내, 메일을 보내려고 접속한 서버의 IP 주소가 도메인 소유자가 허용한 발송 서버 목록에 들어 있는지 확인합니다. 목록에 없다면 발신자 정보가 조작되었을 가능성이 있다고 판단합니다.

SPF가 검사하는 것은 접속한 IP 주소이며, 서버의 호스트명이나 메일 본문은 검사 대상이 아닙니다. 참고로 반송 메일처럼 MAIL FROM이 비어 있는 경우에는 SMTP 접속 시 사용된 HELO/EHLO 도메인을 대신 검사합니다.

레코드를 구성하는 요소

SPF 레코드는 v=spf1로 시작하며, 뒤에 허용할 발송 서버를 지정하는 항목들이 이어집니다.

v=spf1 a:mail.example.net include:spf.maillink.co.kr ~all
항목설명
ip4 / ip6발송 서버의 IP 주소나 대역을 직접 지정합니다.
a지정한 도메인의 A 레코드가 가리키는 IP를 허용합니다.
mx지정한 도메인의 MX 레코드가 가리키는 서버를 허용합니다.
include다른 도메인의 SPF 레코드를 불러와 포함시킵니다. 외부 발송 서비스를 사용할 때 쓰는 항목입니다.
all앞의 어느 항목에도 해당하지 않는 나머지 전부를 의미하며, 항상 맨 뒤에 옵니다.

all 앞에 붙는 기호는 목록에 없는 서버를 어떻게 처리할지 수신 서버에 요청하는 값입니다.

표기의미
-allFail. 목록에 없는 서버의 메일은 거부하도록 요청합니다. 가장 엄격합니다.
~allSoftFail. 의심스럽게 취급하되 거부하지는 않도록 요청합니다. 일반적으로 권장되는 설정입니다.
?allNeutral. 아무런 판단도 하지 않습니다.
+all모든 서버를 허용합니다. SPF를 무력화하는 설정이므로 사용해서는 안 됩니다.

레코드 작성 시 주의할 점

SPF 레코드는 도메인당 하나만 존재해야 합니다

발송 서비스를 추가할 때 v=spf1로 시작하는 TXT 레코드를 하나 더 만드는 실수가 자주 발생합니다. 한 도메인에 SPF 레코드가 둘 이상 있으면 수신 서버는 permerror로 판단하며, 기존에 정상 동작하던 SPF까지 전부 무효가 됩니다. 새로 만들지 말고 기존 레코드 안에 항목을 추가해야 합니다.

DNS 조회는 10회를 넘을 수 없습니다

include, a, mx 등은 각각 DNS 조회를 발생시키며, include로 불러온 레코드 안의 조회까지 모두 합산됩니다. 총 10회를 초과하면 역시 permerror가 되어 SPF 검사에 실패합니다. 여러 발송 서비스를 함께 사용한다면 실제 조회 횟수를 확인해 보시기 바랍니다. ip4와 ip6는 조회를 발생시키지 않으므로 항목 수를 줄여야 할 때 활용할 수 있습니다.

또 한 가지, SPF는 메일이 다른 주소로 자동 전달(포워딩)되면 깨집니다. 전달하는 서버의 IP는 원래 도메인의 허용 목록에 없기 때문입니다. 이는 SPF의 구조적 한계이며, 이런 상황까지 대비하려면 DKIM을 함께 적용해야 합니다.

SPF만으로는 부족한 이유

앞서 설명했듯 SPF가 검사하는 주소는 Return Path이며, 수신자에게 보이는 From 주소와는 무관합니다. 따라서 공격자가 자신이 소유한 도메인을 Return Path로 사용하면서 From에는 다른 회사의 주소를 넣더라도 SPF 검사 자체는 통과할 수 있습니다.

이 간극을 메우는 것이 DMARC의 정렬(alignment) 규칙입니다. DMARC는 SPF 통과 여부뿐 아니라 Return Path 도메인이 From 도메인과 일치하는지까지 확인합니다. 일부 포털이나 기업에서 "Return Path의 SPF를 통과했는데도 메일이 스팸함으로 갔다"는 현상이 나타나는 것은 대부분 이 정렬 조건 때문입니다.

DMARC의 동작 방식과 정책 레코드 작성법은 DMARC에 대하여 알아보기 문서에서 다루고 있습니다.

메일링크 이용 시 SPF 등록 방법

메일링크의 모든 발송 서버에는 SPF 정보가 등록되어 있어, 특별한 예외 상황이 없는 한 수신 서버의 SPF 검사를 정상적으로 통과합니다. 다만 앞서 설명한 정렬 조건까지 충족하려면 고객사 도메인의 DNS에 메일링크 발송 서버 정보를 추가해야 합니다.

메일링크가 이 작업을 대신 처리할 수 없는 이유는 간단합니다. 고객사 도메인의 소유권이 메일링크에 없으므로 해당 DNS 정보를 수정할 권한이 없기 때문입니다.

도메인 공급업체마다 입력 화면은 조금씩 다르지만 등록해야 하는 정보는 동일합니다. 고객사 도메인을 example.net이라고 가정하겠습니다.

입력란입력값
유형(Type)TXT
이름/호스트 @
서브도메인에 적용한다면 서브도메인 식별자만 입력합니다. 예를 들어 sub.example.net이라면 sub를 입력합니다.
값(Value) 기존 SPF 레코드가 없는 경우
v=spf1 include:spf.maillink.co.kr ~all

이미 SPF 레코드가 있는 경우, 새로 만들지 말고 기존 레코드에 include:spf.maillink.co.kr을 추가합니다. 예를 들어 v=spf1 a:mail.example.net ~all이 등록되어 있다면 다음과 같이 수정합니다.
v=spf1 a:mail.example.net include:spf.maillink.co.kr ~all
TTL3600초

include는 항상 all 앞에 위치해야 합니다. ~all 뒤에 추가하면 해당 항목이 무시됩니다.

Return Path 커스터마이징

메일링크는 위 SPF 정보가 정상적으로 등록된 경우, Return Path를 고객사 도메인 계정으로 사용하도록 지원하고 있습니다. 이 설정을 마치면 Return Path 도메인과 From 도메인이 일치하게 되어 DMARC의 SPF 정렬 조건까지 충족됩니다.

등록 후 확인 방법

DNS 반영에는 보통 수십 분에서 하루 정도가 걸립니다. 메일링크 사용자라면 별도의 도구 없이 화면에서 바로 확인하실 수 있습니다.

메일링크 접속 → 이메일 발송 → 보내는이 주소 관리로 이동한 뒤, 목록에 보이는 도메인을 더블클릭하면 정상 등록 여부가 표시됩니다.

직접 DNS를 조회해 확인하려면 아래 명령을 사용합니다.

nslookup -type=TXT example.net

위에서 언급한 spf.maillink.co.kr은 메일링크에서 공용으로 사용하는 발송 서버 정보입니다. 프라이빗 메일링크와 같이 전용 IP 할당 서비스를 이용하는 고객이시라면 메일링크 고객센터(1544-9231 또는 help@maillink.co.kr)로 연락하시면 전용 서버 정보를 전달받으실 수 있습니다.
